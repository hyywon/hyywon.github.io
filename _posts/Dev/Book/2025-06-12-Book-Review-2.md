## 서버 성능 개선 기초

### 병목 지점 🚧

서비스 초기에는 성능 문제가 잘 발생하지 않는다. 사용자 수, 트래픽, 데이터 베이스 크기등 전반적인 서비스가 작기 때문이다.

하지만 사용자가 늘면서 성능 문제는 사용자가 늘면서 점차 발생한다.

이런 증상을 방치하면 어느 순간 심각한 성능 문제가 발생하는데, 전형적인 증상은 아래와 같다.

- 순간적으로 모든 사용자 요청에 대한 응답시간이 심각하게 느려진다. 10초이상 걸리는 요청이 늘어나고 다수의 요청에서 연결 시간 초과와 같은 오류가 발생한다.
- 서버를 재시작하면 잠시 괜찮다가 다시 응답시간이 느려지는 현상이 발생한다.
- 트래픽이 줄어들 때까지 심각한 상황이 계속 유지된다.

트래픽이 증가하면서 성능 문제가 발생하는 주 이유는 시스템이 수용할 수 있는 최대 TPS를 초과하는 트래픽이 유입되기 때문이다. 최대 TPS를 높이지 않으면 증가하는 트래픽을 처리할 수 없게 된다.

✅ TPS를 높이려면 우선 성능 문제가 발생하는 지점을 찾아야 한다.

문제 지점을 찾는 간단한 방법은 처리 시간이 오래 걸리는 작업을 식별하는 것. 성능 문제는 응답시간이 길어지면서 발생하는 경우가 많기 때문이다.

- 오래 걸릴 것 같은 코드를 추측할 수 있지만 가능하면 실제 실행 시간을 측정해야 한다.
- 모니터링 도구를 이용하여 실행 시간 추적 기능을 활용하면 성능 문제가 발생하는 시점에 어떤 코드에서 오래 걸렸는지 찾을 수 있다.
- 모니터링 도구가 없다면, 로그라도 남겨서 추후에 성능 문제가 발생했을 때 개선할 부분을 찾는데 도움이 된다.

✅ 서버 성능문제는 주로 DB 연동이나 API 연동 과정에서 발생한다.

*우선 서버 관점에서 처리량과 응답 시간을 개선하는 방법을 중심으로 살펴보고 추후 DB와 관련한 내용, 외부 연동과 관련된 내용을 정리해 볼 예정이다.*

### **수직 확장 (Scale-up) vs 수평 확장 (Scale-out)**

성능 문제를 일으키는 원인을 찾았다면 빠르게 적용할 수 있는 개선안을 도출해야 한다.

사용자가 서비스를 이용하지 못하는 상황을 방치한 채 시간만 오래 걸리는 개선 방안을 시도할 수는 없다. 일단 급한 불을 끄고 나서 근본적 해결을 모색해야한다.

### 수직 확장 (Scale-up) ⬆

: CPU, 메모리, 디스크 등 자원을 증가시키는 것을 의미한다. 클라우드 환경에서 비교적 빠르게 시도할 수 있는 방법

수직 확장이 DB에서만 효과가 있는 것은 아니다. 서버도 메모리 부족으로 성능 문제가 발생할 수 있다.

예를 들어 서버 메모리가 512MB일 때 동시 처리 가능한 요청수가 200개라면

동시 요청이 250개로 늘어나는 것만으로도 응답 시간이 증가하기 시작한다.

→ 이때 서버 메모리를 1GB로 증설하기만 해도 TPS를 늘릴 수 있다.

> 수직 확장은 즉각적인 효과를 바로 얻을 수 있지만
> 
> 
> 트래픽이 지속해서 증가하면 언젠간 결국 다시 성능 문제가 발생한다.
> 
> 그때마다 수직 확장을 지속할 수 없다. (비용 문제, 용량 한계)
> 

### 수평 확장 (Scale-out) ➡

: 서버를 추가로 설치하는 방식을 의미한다. 즉, 하나의 서버가 처리하던 일을 여러대의 서버가 처리하도록 만들어주는 방법

하지만 TPS를 높이기 위해 무턱대고 서버를 추가해서도 안된다.

실제 병목 지점이 어디인지 파악하는 게 중요하다. DB에 선은 문제가 발생하고 있는데 서버를 추가로 투입하면 더 큰 부하를 일으키게 된다.

외부 API의 성능이 문제인 경우도 동일하다. 외부 API성능이 개선되지 않는 한 서버를 추가한다고 해도 TPS는 향상되지 않는다.

**즉, DB나 외부 API에 성능 문제가 발생하지 않는 범위 내에서 수평확장을 해야 효과가 있다.**
